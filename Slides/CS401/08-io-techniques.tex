\section{The I/O Problem and the I/O Unit}

\begin{frame}{Socratic Question: The Speed Mismatch}
  \begin{block}{Question}
    A CPU runs one instruction about every nanosecond ($10^9$ instructions
    per second). A keyboard produces one keystroke about every 200
    milliseconds (about 5 keystrokes per second). If the CPU must read every
    keystroke, what should it do during the 200~ms between two keystrokes?
  \end{block}
  \begin{itemize}
    \item The CPU is roughly \key{200 million times} faster than the typist
      --- the two operate on completely different time scales.
    \item Waiting wastes the CPU, so I/O design is really the question:
      \emph{who does the waiting}, and \emph{what does the waiting cost}?
    \item Today's four techniques are four answers to that one question.
  \end{itemize}
\end{frame}

\begin{frame}{The Simplest Way In: Memory-Mapped I/O}
  \begin{block}{Memory-mapped I/O}
    A device's \textbf{data}, \textbf{status}, and \textbf{control} registers
    are given addresses in the \emph{normal} memory space. The CPU reads and
    writes a device exactly like it reads and writes memory --- no special
    I/O instructions needed \cite{Hamacher2002_computer_organization}.
  \end{block}
  \begin{itemize}
    \item Plain English: \muted{a device pretends to be a few memory
      locations.}
    \item The alternative --- \key{isolated I/O} --- needs separate I/O
      instructions and a separate address space (the classic IBM
      approach, Mano Ch.~11). Memory-mapped I/O is simpler for this course.
  \end{itemize}
\end{frame}

  \begin{center}

  directly. It talks to three registers inside the device's interface, over

  \begin{itemize}
    \item \key{Data register} --- the byte actually being transferred
      (e.g.\ \texttt{KBD\_DATA} for the keyboard, \texttt{DISP\_DATA} for the
      display).
    \item \key{Status register} --- flags such as \texttt{KIN} (a keystroke is
      waiting) or \texttt{DOUT} (display is ready for the next character).
    \item \key{Control register} --- settings such as interrupt-enable bits.
  \end{itemize}
  \muted{The interface also performs address decoding, timing, and format
  conversion --- the ``six functions'' of an interface circuit, Hamacher
  Ch.~7 \S7.4, p.~238.}

  \footnotesize

    \bottomrule
  \end{tabular}
  \vspace{0.3cm}

  \muted{We use memory-mapped I/O for the rest of the deck --- it is what the
  Hamacher examples assume \cite{Hamacher2002_computer_organization}. The
  isolated form is the standard alternative (Mano Ch.~11).}
\end{frame}

\section{Program-Controlled I/O (Polling)}

\begin{frame}{Definition: Program-Controlled I/O (Polling)}
  \begin{block}{Polling}
    In \textbf{program-controlled I/O} (also called \textbf{polling}), the
    CPU runs a loop that repeatedly reads the device's \emph{status register}
    and checks a ready flag. When the flag says the device is ready, the CPU
    stops the loop and performs the data transfer itself.
  \end{block}
  \begin{itemize}
    \item Plain English: \muted{the CPU keeps asking ``are you ready yet?'' in
      a loop until the answer is ``yes,'' then does the work.}
    \item The device never initiates anything --- it only answers questions.
    \item Two new status flags, one per device direction:
      \key{\texttt{KIN}} (a keyboard keystroke is ready in
      \texttt{KBD\_DATA}) and \key{\texttt{DOUT}} (the display is ready for
      the next character in \texttt{DISP\_DATA}).
  \end{itemize}
\end{frame}

\begin{frame}[fragile]{Worked Example: Two Polling Loops}
  \begin{columns}[T]
    \begin{column}{0.48\textwidth}
      \centering \textbf{Keyboard input}\\[0.15cm]
      \footnotesize Read one keystroke into register \texttt{R}.
      \begin{block}{\texttt{READWAIT} loop}
        \footnotesize
        \begin{verbatim}
READWAIT: Test KIN
          Branch=0 READWAIT
          MoveByte KBD_DATA, R
        \end{verbatim}
      \end{block}
    \end{column}
    \begin{column}{0.48\textwidth}
      \centering \textbf{Display output}\\[0.15cm]
      \footnotesize Send register \texttt{R} to the display.
      \begin{block}{\texttt{WRITEWAIT} loop}
        \footnotesize
        \begin{verbatim}
WRITEWAIT: Test DOUT
           Branch=0 WRITEWAIT
           MoveByte R, DISP_DATA
        \end{verbatim}
      \end{block}
    \end{column}
  \end{columns}
  \vspace{0.2cm}
  \textbf{How to read these loops:}
  \begin{itemize}
    \item \texttt{Test KIN} reads the status flag; \texttt{Branch=0} jumps
      back while the flag is still \texttt{0} (not ready).
    \item Only when the flag turns \texttt{1} does the loop fall through to
      the single transfer instruction.
  \end{itemize}
  \muted{Each pass runs the same two-test instructions again --- the CPU is
  spinning, doing no useful work between keystrokes
  \cite{Hamacher2002_computer_organization}.}
\end{frame}

\begin{frame}{Worked Example: The Cost of Polling, in Numbers}
  \begin{block}{The setup}
    A 2~GHz CPU (one instruction every 0.5~ns) polls a keyboard that produces
    5 keystrokes per second. Each poll takes one 2-instruction pass
    (about 1~ns). Between two keystrokes, how many polls run, and how much
    CPU time do they waste?
  \end{block}
  \begin{itemize}
    \item Gap between keystrokes: $1/5 = 0.2$~s $= 2\times10^8$~ns.
    \item Polls per gap: $2\times10^8$~ns $\div$ 1~ns/poll
      $= 2\times10^8$ \key{polls wasted} per keystroke.
    \item Fraction of CPU consumed by polling: $2\times10^8$~ns $\div$
      $2\times10^8$~ns $= 1.0$ --- the CPU spends \key{100\%} of its time
      waiting on this one keyboard.
  \end{itemize}
  \muted{Moral: polling is trivially simple but hands the CPU over to the
  slowest device in the system.}
\end{frame}

\begin{frame}{Polling: Trade-offs}
  \begin{tabular}{@{}ll@{}}
    \toprule
    \textbf{Advantage} & \textbf{Disadvantage} \\
    \midrule
    No extra hardware needed & Wastes CPU time while waiting \\
    Trivial to implement & CPU cannot do other work during the wait \\
    Works for any device & Cost grows with device slowness \\
    \bottomrule
  \end{tabular}
  \vspace{0.3cm}
  \begin{block}{When polling is (and isn't) a good fit}
    \textbf{Good fit:} one slow device and a CPU with nothing else to do.
    \textbf{Bad fit:} a fast device, or several devices --- the CPU spends
    its life asking questions instead of computing.
  \end{block}
\end{frame}

\section{Interrupt-Driven I/O}

\begin{frame}{Definition: Interrupt and Interrupt-Service Routine}
  \begin{block}{Interrupt}
    An \textbf{interrupt} is a signal from a device that suspends the CPU's
    current program and forces it to jump to a fixed handler --- the
    \textbf{interrupt-service routine (ISR)} --- which services the device.
    When the ISR finishes, the CPU resumes the original program exactly where
    it left off.
  \end{block}
  \begin{center}
    % Diagram: time-flow of control transfer. Main program timeline on the
    % left (time increasing downward); a dashed diagonal arrow at the point
    % of interrupt jumps right to the ISR timeline; a second dashed diagonal
    % arrow returns control to the main program below the interrupt point.
    % Coordinates: (x, y)
    %   Main program line from (0, 3.2) to (0, -2.2)
    %   Interrupt point on main line at (0, 1.6)
    %   ISR line from (6.4, 1.0) to (6.4, -0.8)
    %   Resume point on main line at (0, -1.4)
    \begin{tikzpicture}[scale=0.44, transform shape,
        every node/.style={font=\small}]
      \draw[thick, primary-blue] (0,3.2) -- (0,-2.2);
      \node[font=\scriptsize, anchor=east] at (-0.55,2.8) {Main program};
      \draw[thick, primary-gold] (6.4,1.0) -- (6.4,-0.8);
      \node[font=\scriptsize, anchor=west] at (6.95,0.70) {ISR};
      \filldraw[primary-blue] (0,1.6) circle (2pt);
      \filldraw[primary-blue] (0,-1.4) circle (2pt);
      \draw[dashed, thick, ->] (0,1.6) -- (6.4,1.0)
            node[midway, above, yshift=0.25cm] {\scriptsize interrupt accepted};
      \draw[dashed, thick, ->] (6.4,-0.8) -- (0,-1.4)
            node[midway, below, yshift=-0.28cm] {\scriptsize return (RTI)};
    \end{tikzpicture}
  \end{center}
  \begin{itemize}
    \item \key{Interrupt latency}: the gap between the device's request and
      the CPU's jump --- time during which the device waits.
    \item \key{Shadow registers}: registers where the CPU saves state so the
      ISR can use them freely \cite{Hamacher2002_computer_organization}.
  \end{itemize}
\end{frame}

\begin{frame}{Enabling and Disabling Interrupts: Two Switches}
  \begin{block}{A request reaches the CPU only if \emph{both} switches are on}
    \begin{itemize}
      \item \key{\texttt{IE}} --- one interrupt-enable bit inside the
        processor status register (\texttt{PS}). When \texttt{IE}$=0$, the
        CPU ignores \emph{every} interrupt request, from any device.
      \item A \emph{per-device} interrupt-enable bit in that device's control
        register --- \key{\texttt{KIRQ}} for the keyboard, \key{\texttt{DIRQ}}
        for the display --- decides whether \emph{this} device may request an
        interrupt at all.
    \end{itemize}
  \end{block}
  \begin{itemize}
    \item Plain English: \muted{the master switch is \texttt{IE}; each device
      also has its own little switch. Both must be on for the request to
      arrive.}
    \item Example: \texttt{KIRQ}$=1$ and \texttt{IE}$=1$ means a keystroke
      will interrupt; \texttt{IE}$=0$ means it waits.
  \end{itemize}
\end{frame}

\begin{frame}{Worked Example: A 5-Step Interrupt Scenario}
  \footnotesize
  \textbf{The story:} a keystroke arrives while the CPU is busy running a
  program. Here is exactly what happens, step by step.
  \begin{enumerate}
    \item The device sets its status flag (\texttt{KIN}$=1$) and, if its
      enable bit \texttt{KIRQ} is on, raises an interrupt-request line.
    \item The CPU finishes its \emph{current instruction} (never interrupting
      mid-instruction), then checks the master switch \texttt{PS.IE}.
    \item If \texttt{IE}$=1$: the CPU saves \texttt{PC} (and any registers the
      ISR will overwrite) into shadow registers, disables further interrupts,
      and loads \texttt{PC} with the ISR's starting address.
    \item The ISR services the device --- here, it reads \texttt{KBD\_DATA}
      (which clears \texttt{KIN}) --- then executes a return-from-interrupt
      instruction.
    \item Return-from-interrupt restores the saved \texttt{PC} and re-enables
      interrupts. The interrupted program resumes as if nothing happened
      \cite{Hamacher2002_computer_organization}.
  \end{enumerate}
  \vspace{0.2cm}
  \muted{Notice what the CPU did \emph{not} do: it did not poll. It went on
  computing until the device rang the bell.}
\end{frame}

\begin{frame}{Handling Multiple Devices: Who Interrupted?}
  \begin{block}{Two designs for answering ``which device interrupted?''}
    \begin{itemize}
      \item \textbf{Polling the sources}: on any interrupt, the ISR checks each
        device's status flag in turn to find the one that rang --- simple, but
        the check order costs time proportional to the number of devices.
      \item \textbf{Vectored interrupts}: each device supplies a small
        identifying code; hardware uses it to index straight into an
        \key{interrupt-vector table} --- one ISR starting address per
        device --- and jumps directly there.
    \end{itemize}
  \end{block}
  \begin{itemize}
    \item Plain English: \muted{polling-the-sources asks everyone ``was it
      you?'' in order; a vector table skips the asking and goes straight to
      the right ISR.}
    \item Trade-off: a little extra hardware (the table + lookup) buys
      \key{constant-time dispatch}, no matter how many devices
      \cite{Hamacher2002_computer_organization}.
  \end{itemize}
\end{frame}

  \begin{center}

  \textbf{What this diagram shows:} \texttt{IPENDING} latches \emph{which}
  devices currently want an interrupt; \texttt{IENABLE} decides \emph{which of
  those} are allowed through; the priority encoder picks the highest-priority
  allowed one; the vector table gives its ISR address.
  \muted{If the lower-priority device's request stays pending while the higher
  one is being serviced, it waits until interrupts are re-enabled --- or, with
  \key{nesting}, a higher-priority request can interrupt the ISR itself.}
\end{frame}

\begin{frame}{Exceptions: The General Form of an Interrupt}
  \begin{block}{Exception}
    An \textbf{exception} is any event that interrupts the normal flow of
    control --- an I/O interrupt, but also divide-by-zero, an illegal
    instruction, a page fault, or a timer tick. The interrupt mechanism is the
    same; only the \emph{source} differs
    \cite{Hamacher2002_computer_organization,PattersonHennessy2017_computer_organization_design}.
  \end{block}
  \begin{itemize}
    \item Plain English: \muted{an interrupt is just one kind of exception ---
      the ``a device needs me'' kind.}
    \item Thinking of them together matters because the CPU handles them with
      the same jump-to-handler machinery: save state, service, restore.
    \item This is the bridge the next lectures will reuse: exceptions are how
      the OS gets control back from user programs.
  \end{itemize}
\end{frame}

\begin{frame}{Socratic Check: Simultaneous Interrupt Requests}
  \begin{alertblock}{Question}
    Device 1 (higher priority) and Device 2 both request an interrupt on the
    same cycle. Device 1's ISR is still running when Device 2's request would
    normally be granted. What happens?
  \end{alertblock}
  \begin{itemize}
    \item If \textbf{nesting} is allowed and Device 2 outranks whatever
      priority level Device 1's ISR is running at, Device 2 can interrupt
      \emph{that ISR} --- the same 5-step scenario applies recursively.
    \item If nesting is disabled (or Device 2 is lower priority), Device 2's
      request stays latched in \texttt{IPENDING} until Device 1's ISR
      re-enables interrupts.
  \end{itemize}
\end{frame}

\begin{frame}{Polling vs.\ Interrupts: The Trade-off}
  \footnotesize
  \begin{tabular}{@{}lll@{}}
    \toprule
    & \textbf{Polling} & \textbf{Interrupts} \\
    \midrule
    Who initiates & CPU (asks repeatedly) & Device (signals once, when ready) \\
    CPU cost while waiting & Wasted spin cycles & Zero --- CPU runs other code \\
    Extra hardware & None & \texttt{IE}, per-device enables, vector table \\
    Response latency & Depends on poll rate & Interrupt latency (usually smaller) \\
    Best fit & One slow device, nothing else to do & Multiple/unpredictable devices \\
    \bottomrule
  \end{tabular}
  \vspace{0.3cm}
  \key{Same problem, opposite direction of initiative} --- interrupts move
  the waiting cost from the CPU to the hardware that detects readiness.
\end{frame}

\section{Synchronous vs.\ Asynchronous Bus}

\begin{frame}{Bus Structure: Master and Slave Roles}
  \begin{block}{One shared bus, many devices}
    Every I/O interface from Act 1 hangs off a single shared \textbf{bus} ---
    address, data, and control lines that every device listens to. A
    \textbf{bus protocol} is the rulebook for how a \textbf{master} (the
    device driving a transfer, usually the CPU) and a \textbf{slave} (the
    device responding) coordinate one data transfer without colliding.
  \end{block}
  \begin{itemize}
    \item \key{This Act's question}: when the master says ``take this data'' or
      ``give me that data,'' how does the slave say ``not ready yet'' or ``here
      it is''?
    \item Two different answers: \key{synchronous} (everyone shares a clock)
      and \key{asynchronous} (an explicit handshake, no clock)
      \cite{Hamacher2002_computer_organization}.
  \end{itemize}
\end{frame}

\begin{frame}{Definition: Synchronous Bus}
  \begin{block}{Synchronous bus}
    All devices share a common \textbf{bus clock}. The master places the
    address and data on the bus at a fixed clock edge; every slave samples
    the bus at the \emph{same} edge, with no per-transfer negotiation.
  \end{block}

\end{frame}

\begin{frame}{Definition: Asynchronous Bus (Full Handshake)}
  \begin{block}{Asynchronous bus}
    No shared clock. Master and slave exchange explicit
    \textbf{Master-ready}/\textbf{Slave-ready} signals, each one changing only
    \emph{in response to} the other --- a \key{full handshake}.
  \end{block}
  \begin{center}
    % Diagram: 4-step interlocked ladder, Master column left, Slave column
    % right, alternating diagonal arrows. Step numbers are placed OUTSIDE the
    % two columns (not at the arrow midpoints) next to the column point where
    % that step's signal actually changes -- the arrow midpoints all share the
    % same x-midpoint and a pitch of only 0.6 units, too tight for a circled

  arriving at slightly different times) never causes a false sample, unlike
  a synchronous bus's single fixed clock edge \cite{Hamacher2002_computer_organization}.}
\end{frame}

\begin{frame}{Synchronous vs.\ Asynchronous: The Trade-off}
  \footnotesize
  \begin{tabular}{@{}lll@{}}
    \toprule
    & \textbf{Synchronous} & \textbf{Asynchronous} \\
    \midrule
    Timing reference & Shared bus clock & Explicit handshake, no clock \\
    Slow-device handling & Extra wait-state clock cycles & Handshake simply takes longer \\
    Skew sensitivity & Sensitive --- must beat clock period & Immune --- self-timed \\
    Per-transfer overhead & Low (one clock edge) & Higher (two round trips) \\
    Best fit & Devices of similar, known speed & Mixed-speed / unpredictable devices \\
    \bottomrule
  \end{tabular}
  \vspace{0.3cm}
  \key{Same coordination problem, opposite mechanism} --- a shared clock
  everyone trusts, or an explicit conversation that trusts nothing.
\end{frame}

\begin{frame}{Socratic Check: Why Not Always Use Asynchronous?}
  \begin{alertblock}{Question}
    Asynchronous handshaking tolerates skew and adapts automatically to any
    device speed. Why do most high-speed processor buses use synchronous
    protocols instead?
  \end{alertblock}
  \begin{itemize}
    \item Every asynchronous transfer pays \emph{two full round-trip delays}
      (steps 1--2 and 3--4) --- for consistently fast devices this is pure
      overhead a synchronous bus does not pay.
    \item Synchronous buses only lose when a device is unusually slow (extra
      wait states) or the clock must shrink to accommodate skew --- exactly
      the trade-off the comparison table names.
  \end{itemize}
\end{frame}

\section{DMA and I/O Processors}

\begin{frame}{The Cost Interrupts Still Pay}
  \begin{block}{Socratic question}
    A disk transfer moves a 4096-byte block, one 4-byte word at a time. With
    interrupt-driven I/O, the ISR executes on \emph{every word}: read status,
    read/write data, update a memory pointer, decrement a counter, return.
    What does this cost for one block?
  \end{block}
  \begin{itemize}
    \item Words per block: $4096 \div 4 = \key{1024}$ words.
    \item That means \key{1024 ISR invocations} for a single block transfer
      --- one interrupt per word.
    \item Interrupts removed the CPU's \emph{waiting}, but not its
      \emph{involvement in moving every byte}. The next step removes the CPU
      from the data path itself.
  \end{itemize}
\end{frame}

\begin{frame}{Bus Arbitration: A Third Role for a Device}

  one requester, by priority, each time

\begin{frame}{From Arbitration to Direct Memory Access}
  \begin{block}{The functional idea, stated plainly}
    Once a device can become bus master, it can transfer data \emph{directly
    to or from memory} --- no CPU instruction touches the data at all. The
    CPU is interrupted \emph{once}, when the whole block finishes, not once
    per word.
  \end{block}
  \muted{This edition of Hamacher's text (Ch.~7, arbitration) describes
  exactly this mechanism but never names it ``DMA'' --- the term and its
  standard treatment below follow Stallings Ch.~8
  \cite{Stallings2015_computer_organization}, per the syllabus and
  \texttt{.claude/rules/textbook-grounding.md}.}
\end{frame}

\begin{frame}{Definition: Direct Memory Access (DMA)}
  \begin{block}{DMA (general/standard treatment --- Stallings Ch.~8)}
    A \textbf{DMA controller} is given a source/destination address and a
    word count by the CPU, then becomes bus master (via arbitration) and
    transfers the entire block directly to/from memory, interrupting the CPU
    only when the \emph{block} --- not each word --- is complete
    \cite{Stallings2015_computer_organization}.
  \end{block}
  \begin{itemize}
    \item Plain English: \muted{the CPU says ``copy this block,'' then goes
      back to work; the DMA controller does the copying and rings the bell
      when done.}
    \item \good{Pro}: CPU cost drops from 1024 ISRs to ``one setup, one
      completion interrupt'' --- a constant cost regardless of block size.
    \item \bad{Con}: the DMA controller and CPU now compete for the same
      memory bus (\textbf{cycle stealing}); extra hardware required.
  \end{itemize}
\end{frame}

  \begin{itemize}

    \item \key{Word count} --- how many words remain to transfer; decremented
      after every word.
    \item \key{Control/status} --- transfer direction, mode, and the
      ``block done'' flag that interrupts the CPU.
  \end{itemize}
  \muted{The CPU writes all four registers once at setup; the DMA controller
  owns them from then on.}

\begin{frame}{How a DMA Transfer Runs: Step by Step}
  \footnotesize
  \textbf{The story:} copy the 4096-byte block from the disk to memory. The
  CPU appears twice --- at setup and at completion --- and never touches the
  data itself.
  \begin{enumerate}
    \item \textbf{Setup:} the CPU writes the DMA controller's registers ---
      source address (disk), destination address (memory), word count (1024),
      and direction (read) \cite{Stallings2015_computer_organization}.
    \item \textbf{Request:} the DMA controller asks for the bus by asserting
      \texttt{BR} (bus request).
    \item \textbf{Grant:} the arbiter answers with \texttt{BG} (bus grant);
      the DMA controller becomes bus master
      \cite{Hamacher2002_computer_organization}.
    \item \textbf{Transfer one word:} the DMA controller reads one word from
      the device and writes it to memory (or the reverse), using one or two
      bus cycles.
    \item \textbf{Decrement:} it subtracts 1 from the word count and, if the
      count is still $>0$, returns to step 2 for the next word.
    \item \textbf{Done:} when the count reaches 0, the DMA controller drops
      \texttt{BR} and raises a \emph{completion interrupt} --- the CPU's only
      involvement after setup.
  \end{enumerate}
  \vspace{0.2cm}
  \muted{Compare with polling/interrupts: the CPU now appears exactly twice,
  at the start and the end.}
\end{frame}

\begin{frame}{DMA Transfer Modes: Three Ways to Use the Bus}
  \begin{block}{How long does the DMA controller keep the bus?}
    \begin{itemize}
      \item \key{Burst (block) mode}: holds the bus for the \emph{entire}
        block --- all 1024 words in one continuous burst, then releases and
        interrupts the CPU.
      \item \key{Cycle-stealing (single) mode}: grabs the bus for \emph{one
        word}, releases it, re-requests --- the CPU can use the bus between
        DMA words.
      \item \key{Transparent (hidden) mode}: transfers \emph{only during CPU
        cycles that do not use the bus at all} --- the CPU never even notices
        the DMA happening.
    \end{itemize}
  \end{block}
  \footnotesize
  \begin{tabular}{@{}llll@{}}
    \toprule
    & \textbf{Burst} & \textbf{Cycle stealing} & \textbf{Transparent} \\
    \midrule
    Bus held & Whole block & One word & Only idle CPU cycles \\
    Transfer speed & Fastest & Medium & Slowest \\
    Effect on CPU & Starved for the block & Brief pauses per word & None \\
    \bottomrule
  \end{tabular}
  \vspace{0.2cm}
  \normalsize
  \muted{Plain English: burst = ``whole job now, don't bother me''; cycle
  stealing = ``one word, then back off''; transparent = ``only when you're not
  looking.''}
\end{frame}

\begin{frame}{Worked Example: How Much CPU Does DMA Save?}
  \begin{block}{The comparison}
    Same 4096-byte block as the interrupt example. Interrupt-driven I/O: 1024
    ISRs. DMA: one setup + one completion interrupt. Suppose one ISR takes
    200 CPU instructions; how many instructions does each technique spend?
  \end{block}
  \begin{itemize}
    \item Interrupts: $1024 \times 200 = \key{204{,}800}$ instructions.
    \item DMA: one setup + one completion ISR $\approx 400$ instructions ---
      roughly \key{500$\times$ less} CPU work.
    \item The CPU that used to spend its whole time servicing the disk can
      now run the user's program instead.
  \end{itemize}
\end{frame}

\begin{frame}{Definition: I/O Processor (IOP)}
  \begin{block}{IOP (general/standard treatment --- Stallings Ch.~8)}
    An \textbf{I/O processor} generalizes DMA one step further: a dedicated
    processor, given a whole \emph{channel program} (a short program
    describing several transfers, formats, and simple decisions), executes it
    independently --- interrupting the main CPU only when the entire program
    completes, not per block.
  \end{block}
  \begin{itemize}
    \item Plain English: \muted{DMA copies one block; an IOP runs a whole
      to-do list of I/O jobs and reports back when the list is done.}
    \item The difference is \emph{how much decision-making is delegated} away
      from the CPU, not just how the data moves.
  \end{itemize}
\end{frame}

\begin{frame}{Four I/O Techniques, Head to Head}
  \tiny
  \begin{center}
  \begin{tabular}{@{}lllll@{}}
    \toprule
    & \textbf{Polling} & \textbf{Interrupts} & \textbf{DMA} & \textbf{IOP} \\
    \midrule
    CPU cost / word & Every poll & Every word (ISR) & None (setup only) & None \\
    CPU cost / block & --- & Thousands of ISRs & One interrupt & One interrupt \\
    Extra hardware & None & Vector table, \texttt{IE} & DMA controller & Dedicated processor \\
    Best fit & One slow device & Multiple/sporadic devices & Bulk block transfer & Complex I/O subsystems \\
    \bottomrule
  \end{tabular}
  \end{center}
  \vspace{0.3cm}
  \normalsize
  \key{Same core question, four answers}: who watches the device, and how
  much of the CPU does watching cost?
\end{frame}

\begin{frame}{Socratic Check: Choosing a Technique}
  \begin{alertblock}{Question}
    A system reads one temperature sensor value per second (low rate,
    latency-tolerant) and separately copies a 10~MB file from disk to memory
    (high rate, throughput-critical). Which technique fits each?
  \end{alertblock}
  \begin{itemize}
    \item Temperature sensor: \key{interrupts} --- rate is low, so ISR
      overhead per event is negligible, and the CPU is free the rest of the
      time.
    \item Disk copy: \key{DMA} --- per-word CPU involvement at that data rate
      would dominate CPU time; DMA reduces it to one setup, one completion
      interrupt.
    \item \muted{Rule of thumb: match the technique to the \emph{rate} and
      \emph{size} of the transfer, not to habit.}
  \end{itemize}
\end{frame}

\section{Synthesis}

\begin{frame}{The Four Threads Meet}
  \begin{block}{Every design choice moves the waiting cost somewhere else}
    \begin{itemize}
      \item \textbf{Polling vs.\ interrupts (programmer's view):} polling
        wastes CPU cycles asking; interrupts let the device ask instead, at
        the cost of vector-table/priority hardware.
      \item \textbf{Synchronous vs.\ asynchronous (bus hardware):} a shared
        clock is cheap per transfer but skew-sensitive; a handshake is
        skew-immune but pays two round trips every time.
      \item \textbf{Interrupts vs.\ DMA/IOP (who moves the data):}
        interrupts still touch every word; DMA and IOP remove the CPU from
        the data path, trading extra hardware for near-zero per-word cost.
    \end{itemize}
  \end{block}
  None of these is free --- exactly the pattern Weeks 5--7 established for
  buses and control units, now applied to the world outside the chip.
\end{frame}

\begin{frame}{Bridge to Week 9}
  \begin{exampleblock}{From moving data to storing it efficiently}
    Weeks 1--8 built a CPU that computes, controls itself, and now moves data
    to and from slow devices. Week 9 asks: once data is in memory, how do we
    make \emph{memory itself} fast enough to keep up with the CPU?
  \end{exampleblock}
  \begin{itemize}
    \item DRAM is far slower than the CPU --- the same speed-mismatch problem
      this week solved for devices reappears for memory itself.
    \item Cache memory, mapping functions, and replacement policies are
      Week 9's answer.
  \end{itemize}
\end{frame}

\begin{frame}{Summary}
  \begin{itemize}
    \item \key{Memory-mapped I/O}: device registers (data/status/control)
      live in the normal address space; \key{polling} repeatedly tests a
      status flag (\texttt{KIN}, \texttt{DOUT}).
    \item \key{Interrupts}: the device signals readiness; \texttt{PS.IE} and
      per-device enables (\texttt{KIRQ}/\texttt{DIRQ}) gate delivery;
      \key{vectored interrupts} use \texttt{IPENDING}/\texttt{IENABLE} plus
      an interrupt-vector table for constant-time dispatch.
    \item \key{Synchronous bus}: shared clock, wait states for slow slaves.
      \key{Asynchronous bus}: \texttt{Master-ready}/\texttt{Slave-ready} full
      handshake, skew-immune but higher per-transfer overhead.
    \item \key{Bus arbitration} (\texttt{BR}/\texttt{BG}) lets a device
      become bus master --- the functional basis for \key{DMA} (block
      transfer, one completion interrupt) and \key{IOP} (whole channel
      programs, general/standard treatment per Stallings Ch.~8).
    \item \key{Four techniques, one trade-off axis}: how much of the CPU does
      watching and moving the data cost, and how much hardware buys that
      cost down.
  \end{itemize}
\end{frame}
